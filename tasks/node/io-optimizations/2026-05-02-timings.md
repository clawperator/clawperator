# Snapshot latency timing - 2026-05-02

## Summary

Warm daemon-backed `snapshot` calls are currently much faster on the emulator than the
older handoff numbers in `findings.md`.

| Screen | CLI warm daemon mean | Median | Min | Max | Payload | Direct daemon mean |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Google Home | 198.5 ms | 195.2 ms | 179.5 ms | 257.4 ms | 57,083 bytes | 77.7 ms |
| Google Play Store | 199.7 ms | 199.7 ms | 187.5 ms | 211.8 ms | 46,091 bytes | 66.9 ms |
| AirTouch | 187.9 ms | 189.8 ms | 171.8 ms | 197.3 ms | 10,828 bytes mean | 75.6 ms |

Main interpretation:

- The remaining one-shot CLI wall time is now mostly host-side CLI/proxy overhead, not Android UI traversal.
- Android operator snapshot work was small on these screens: about 5.2 ms to 13.8 ms mean.
- Host daemon execution from first recorded preflight event through envelope receipt was about 49 ms to 59 ms mean.
- Starting a fresh CLI process and getting through argument parsing, daemon readiness/version checks, HTTP proxying, result parsing, snapshot attachment, and JSON output adds about 139 ms to 140 ms mean.
- A direct Unix-socket daemon call, which skips fresh CLI process startup and proxy readiness checks, already reaches 66 ms to 78 ms mean.

Compared with the previous `findings.md` warm daemon median of 846 ms, the measured
CLI medians here are 76 percent to 78 percent lower. This is a fresh emulator
baseline and should replace the older physical-device-ish intuition for this
specific environment.

## Methodology

Primary timing used the normal CLI `snapshot` command with daemon enabled:

```bash
node apps/node/dist/cli/index.js snapshot \
  --device emulator-5554 \
  --operator-package com.clawperator.operator \
  --timeout 30000 \
  --format json
```

For each app:

- Launched the app with `adb shell am start -n <package>/<activity>`.
- Waited 5 seconds for the representative screen to settle.
- Started a warm daemon for the release package.
- Ran 3 warmup snapshots.
- Cleared logcat before measured calls.
- Ran 10 measured snapshots through the same already-running daemon.
- Parsed the returned JSON and confirmed a successful envelope with non-empty
  snapshot text.
- Recorded wall-clock time using Node `performance.now()`.
- Recorded payload bytes from returned snapshot text.
- Parsed host logs and logcat by `commandId`.

Summarized per-call JSON artifacts are under:

```text
tasks/node/io-optimizations/2026-05-02-timing-artifacts/
```

Raw logcat and host log captures were used for parsing, then removed from the
worktree to avoid keeping screen text in task artifacts.

I also ran a comparison that POSTed equivalent executions directly to the
daemon's Unix socket at `/execute`. That comparison is not the primary baseline,
but it is useful because it removes fresh CLI process startup and most outer
daemon proxy readiness work.

## Instrumentation

Current logs already provide:

- Host preflight pass
- Host broadcast dispatched
- Host envelope received
- Android command start
- Android `logUiTree` stage start and success
- Android canonical `[Clawperator-Result]`

For the Android sub-breakdown, I added a release-build timing log around
`TaskScopeDefault.logUiTree`:

- hierarchy build: `uiTreeInspector.getCurrentUiHierarchyDump()`
- large hierarchy `Log.d(...)` call
- node counting plus window metadata

This emits `[SnapshotTiming] commandId=...` lines only when Android loggability
for `ClawpSnapshotTiming` is set to `DEBUG`. Normal release behavior pays only a
single `Log.isLoggable(...)` check per snapshot.

Enable for a measurement run with:

```bash
adb -s emulator-5554 shell setprop log.tag.ClawpSnapshotTiming DEBUG
```

Disable by clearing or lowering that log tag property.

## Interpretation

The current bottleneck is not Android traversal/serialization on these screens.
The Android hierarchy build itself was only about 1 ms to 4 ms per call, and the
whole Android snapshot step was generally below 22 ms.

Payload size is not currently the first optimization target for these screens.
Payload does matter because the direct daemon path still has to extract snapshot
text from logcat and serialize it back through the daemon HTTP response, but the
large 57 KB Google Home payload did not produce proportionally worse direct
daemon latency than the 10 KB AirTouch payload.

Transport is still relevant, but not in the old "broadcast plus logcat takes one
second" sense. The measured broadcast-to-envelope interval is single-digit to
low-double-digit milliseconds. The larger daemon-side cost before broadcast is
the readiness/preflight/logcat-attach path, around 46 ms to 52 ms mean.

The largest remaining cost for repeated CLI calls is starting a new Node CLI
process and going through the daemon proxy machinery for every call. That adds
about 140 ms on this machine. If callers need multiple snapshots per second,
they should not repeatedly spawn the CLI. They need a persistent client surface:
daemon socket, serve API, MCP server, or an explicit batch/watch mode.

## Comparison with `findings.md`

`findings.md` reported a warm daemon median of 846 ms. Current medians:

| Screen | Current median | Delta vs 846 ms |
| --- | ---: | ---: |
| Google Home | 195.2 ms | -650.8 ms, -76.9% |
| Google Play Store | 199.7 ms | -646.3 ms, -76.4% |
| AirTouch | 189.8 ms | -656.2 ms, -77.6% |

The old note said the remaining floor was mostly Android UI traversal, app
readiness, and broadcast/logcat behavior. That no longer appears true for this
emulator baseline. The floor has moved up-stack into per-call host process and
proxy overhead.

## Recommended next experiments

1. Measure and optimize a persistent public API path.
   - Run the same 10-call test through `clawperator serve` or MCP over one
     already-running Node process.
   - Likely impact: high.
   - Risk: low if it is measurement first.

2. Add a first-class low-latency snapshot path on the daemon.
   - Expose a supported direct daemon/client API or keep a persistent CLI mode
     so callers avoid fresh Node startup and repeated daemon readiness checks.
   - Likely impact: high, because direct daemon is already 67 ms to 78 ms.
   - Risk: medium if it becomes public contract surface.

3. Cache or reduce warm preflight/logcat-attach work inside the daemon.
   - The daemon spends about 46 ms to 52 ms mean before broadcast after the APK
     check has passed.
   - Likely impact: medium.
   - Risk: medium, because readiness checks are safety-critical.

4. Keep Android snapshot filtering and compact payload work as second-order.
   - Still useful for very complex screens and agent ergonomics.
   - Current emulator data does not make it the fastest path to multiple
     snapshots per second.
   - Likely impact: screen-dependent.
   - Risk: low to medium if opt-in.

5. Re-run on a physical device.
   - The emulator is now fast enough that host overhead dominates.
   - A slower physical device may move the bottleneck back toward Android
     traversal or logcat transport.
   - Likely impact: medium for confidence.
   - Risk: low.

## Failed runs and caveats

- `adb shell monkey ...` returned status 251 on this emulator, so the harness
  switched to explicit `am start -n <package>/<activity>` launches.
- One early warmup hit `logcat exited before terminal envelope (code=255)`.
  The harness retries warmup/measurement calls up to 3 times. No measured calls
  in the final tables failed.
- AirTouch changed from a 28-node to 31-node snapshot during the measured run,
  which is why payload bytes vary.
- The direct daemon comparison was performed after the CLI baseline and is a
  supporting comparison, not the primary requested CLI-style baseline.
- The timing sub-breakdown used Android logging that is now retained behind the
  `ClawpSnapshotTiming` loggability gate.
