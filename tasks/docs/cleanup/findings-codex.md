## Executive Summary

The docs have a strong foundation: the nav is compact, most API pages name their source files, the authored API pages often include concrete JSON, and the build pipeline already distinguishes authored docs from code-derived content. The main IA problem is not lack of material. It is unclear ownership and excessive repetition across the CLI reference, authored API pages, and command-specific pages.

Highest-impact recommendations:

1. Recast `/api/cli/` as a generated command index, not a full inline reference. It should list command, primary syntax, one-line summary, and canonical detail link. It should not print every alias and every flag inline.
2. Define stable canonical anchors for each public surface type: CLI commands, CLI subcommands, execution action types, selector fields and flags, error codes, result-envelope fields, serve endpoints, and setup steps.
3. Make authored pages own behavior, failure modes, examples, and recovery. Make generated sections own enumerations and drift detection. Do not let generated pages become the reader-facing explanation for complex behavior.
4. Add a lightweight link and ownership manifest before considering autolinking. Generic words such as `setup`, `open`, `read`, `type`, and `wait` are too noisy for broad post-processing.
5. Add docs checks that enforce canonical-page ownership and catch unlinked command or action references in authored prose, with an allowlist for generic or local examples.

## Current Docs Map

The docs site uses `sites/docs/mkdocs.yml` with `docs_dir: .build`, strict mode, redirect maps for old paths, and a compact nav. The API nav currently contains Overview, CLI Reference, Logging, Actions, Selectors, Snapshot Format, Errors, Devices, Doctor, Timeouts, Environment Variables, Serve API, Daemon, MCP Server, Navigation Patterns, and Recording Format.

The assembly pipeline is:

1. `docs/` owns authored markdown.
2. `sites/docs/source-map.yaml` declares one fully code-derived page: `api/cli.md`.
3. `source-map.yaml` also declares marker expansions for error codes, selector flags, and MCP tool summary.
4. `.agents/skills/docs-build/scripts/assemble.py` validates nav pages, clears `sites/docs/.build/`, copies authored pages, writes code-derived pages, expands markers, and validates that staged markdown exactly matches the nav.
5. `./scripts/docs_build.sh` then builds the public MkDocs site.

The current `/api/cli/` page is generated by `generate_cli_reference.py` from `apps/node/src/cli/registry.ts`. It parses `COMMANDS[...]`, `synonyms`, `group`, `summary`, `topLevelBlock`, `documentedFlags`, `supportedFlags`, and `subtopics`. It renders:

- one all-command summary table
- one grouped table per command group
- one per-command bullet section per command

The generated CLI page is 360 lines in the current local output. It repeats the same command, syntax, alias, flag, and summary data three times for many commands.

## Source-of-Truth Model

Recommended ownership:

| Surface | Canonical owner | Generated, authored, or linked |
| --- | --- | --- |
| CLI command existence, primary name, group, short summary | `apps/node/src/cli/registry.ts` | Generated index in `/api/cli/` |
| CLI primary syntax | `registry.ts` `topLevelBlock` or a stricter command metadata field | Generated index in `/api/cli/`, linked to detail page |
| CLI aliases and compatibility synonyms | `registry.ts` parser metadata | Generated but collapsed or hidden from primary reading path; detail pages mention only when important |
| CLI flags and aliases | command parser code plus `registry.ts` metadata | Generated verification table per command or command family, but not all inline on `/api/cli/` |
| Execution action types and params | `apps/node/src/contracts/execution.ts` plus execution validation/builders | Authored canonical page `docs/api/actions.md`, with generated action-type index if practical |
| Selectors and selector flags | `contracts/selectors.ts` and `cli/selectorFlags.ts` | Authored canonical page `docs/api/selectors.md` plus generated selector flag marker |
| Result envelope | `contracts/result.ts` and `runExecution` result wrapper | Authored canonical page `docs/api/overview.md` or a dedicated `api/result-envelope.md`; other pages link |
| Error codes | `contracts/errors.ts` | Authored canonical page `docs/api/errors.md` plus generated complete enum table |
| Setup and Operator behavior | installer, operator setup/remediate commands, doctor checks | Authored canonical `docs/setup.md` for user path; `docs/api/doctor.md`, `docs/api/devices.md`, and a possible `api/operator.md` for contracts |
| Serve API endpoints | `apps/node/src/cli/commands/serve.ts` | Authored canonical `docs/api/serve.md`; optional generated endpoint summary later |
| Examples | authored docs verified against code | Authored only, with generated snippets only where they come directly from command metadata |

Precise terminology:

- A CLI command is a shell surface registered in `apps/node/src/cli/registry.ts`, such as `snapshot`, `click`, `doctor`, `serve`, or `recording`.
- A CLI subcommand is a nested shell surface under a CLI command, such as `operator setup`, `recording export`, or `daemon status`.
- An execution action type is a JSON payload action `actions[i].type`, such as `click`, `open_app`, `snapshot`, or `wait_for_navigation`.
- A Node contract is a TypeScript API shape under `apps/node/src/contracts/`, such as `Execution`, `NodeMatcher`, `ClawperatorError`, or `ResultEnvelope`.
- A serve endpoint is an HTTP/SSE route created by `createServeApp()` in `serve.ts`, such as `POST /execute` or `GET /events`.
- A selector concept is either a raw `NodeMatcher` field or a CLI selector flag that maps to one.
- An error concept is a public error code in `ERROR_CODES`, a runtime envelope error string, or a route-local serve wrapper code. These should be distinguished.
- A result envelope is the Android terminal envelope prefixed by `[Clawperator-Result]`; the CLI and serve layers may wrap it.

## Findings

### Finding 1: `/api/cli/` Is A Repetitive Reference Dump Instead Of A Useful Command Index

Severity: High

Surface: `sites/docs/.build/api/cli.md`, `.agents/skills/docs-build/scripts/generate_cli_reference.py`, `apps/node/src/cli/registry.ts`

Evidence:

- `source-map.yaml` makes `api/cli.md` a fully generated page from `generate_cli_reference.py`.
- `generate_cli_reference.py` renders a global table in `render_table()`, then repeats grouped tables and per-command bullet blocks in `render_group()`.
- The local generated page is 360 lines and repeats the same command metadata three times for common commands.
- The `skills` row includes a long syntax cell with many subcommands and a flags cell containing primary and compatibility aliases such as `--device-id`, a legacy package-name alias, and `--timeout-ms`.

Why it matters for humans:

The page is hard to skim. A human looking for the right command has to scan dense tables with long cells and many aliases. The page looks generated in the bad sense: accurate-ish, but not curated.

Why it matters for agents:

Agents may over-weight compatibility aliases or copy secondary forms because they are shown at the same visual level as primary forms. The page also buries the canonical next place to read, because commands are not linked to richer canonical behavior pages.

Recommendation:

Make `/api/cli/` a generated command index. Keep command name, primary syntax, one-line summary, and canonical detail link. Move flags, aliases, examples, and failure modes to canonical command or concept pages. If aliases are retained, collapse them into a secondary "Accepted aliases" detail section per command or omit them from the index unless the alias is important for migration.

### Finding 2: There Is No Explicit Canonical Link Contract For CLI Commands

Severity: High

Surface: `sites/docs/mkdocs.yml`, generated `api/cli.md`, authored `docs/api/*.md`

Evidence:

- `mkdocs.yml` nav has one generated `API > CLI Reference` page, but no command-level pages or command-specific nav entries.
- Generated headings such as `### \`snapshot\`` create anchors incidentally, but they are not declared as a stable contract.
- Authored pages describe commands in different places: `docs/setup.md` owns the setup flow, `docs/api/devices.md` owns `clawperator devices`, `docs/api/doctor.md` owns `clawperator doctor`, `docs/api/serve.md` owns `clawperator serve`, `docs/api/recording.md` owns recording commands, and `docs/api/logging.md` owns `clawperator logs`.
- Many command mentions in authored docs are plain code spans rather than links to canonical entries.

Why it matters for humans:

Readers cannot tell whether `clawperator snapshot` should be understood from `/api/cli/`, `/api/snapshot/`, `/api/actions/`, or `/setup/`. This lowers trust because repeated facts feel accumulated rather than designed.

Why it matters for agents:

Agents retrieve by exact phrase and stable URL. If command mentions are not linked to canonical pages, an agent may pull the generated table instead of the page with behavior, output shape, and recovery.

Recommendation:

Define a command link manifest. For example:

- `snapshot` -> `api/snapshot.md#clawperator-snapshot` or `api/cli.md#snapshot` depending on whether behavior is canonical on Snapshot Format or the command index
- `doctor` -> `api/doctor.md#command`
- `devices` -> `api/devices.md#clawperator-devices`
- `serve` -> `api/serve.md#start-the-server`
- `recording start`, `recording export`, etc. -> `api/recording.md#start`, `#export`, etc.
- `operator setup` -> `setup.md#3-install-the-operator-apk` for setup flow and possibly a future `api/operator.md#operator-setup` for contract details

Keep `/api/cli/` as the directory that links to these owners, not the page that tries to own all details.

### Finding 3: "API Call" Is Ambiguous Across The Docs IA

Severity: Medium

Surface: `docs/api/overview.md`, `docs/api/actions.md`, `docs/api/serve.md`, `docs/api/mcp.md`, `docs/api/cli.md`

Evidence:

- The repo has multiple public surfaces: CLI commands, JSON execution action types, TypeScript contract shapes, HTTP endpoints, MCP tools, selector fields, error codes, and terminal result envelopes.
- `docs/api/overview.md` defines execution payload and result envelope.
- `docs/api/actions.md` defines action types and includes a CLI-to-action mapping.
- `docs/api/serve.md` defines HTTP endpoints.
- `docs/api/mcp.md` defines MCP tools.
- Generated `/api/cli/` is also under API and lists shell commands.

Why it matters for humans:

People coming from product docs may assume "API" means HTTP. People coming from the Node package may assume TypeScript imports. People using the CLI may assume shell commands. The nav currently puts all of these under one API bucket without a strong taxonomy.

Why it matters for agents:

Agents need to choose the right actuation surface. If "API call" can mean `clawperator click`, `POST /execute`, `actions[].type = "click"`, or MCP `click`, retrieval and planning can mix incompatible shapes.

Recommendation:

Add a short "Surface Map" near the top of `docs/api/overview.md` and/or `docs/index.md` that defines each surface and links to the canonical page. Use stable labels:

- CLI commands
- Execution actions
- Node contracts
- Serve endpoints
- MCP tools
- Selectors
- Errors
- Result envelope

Then use those labels consistently in page intros and link text.

### Finding 4: CLI Detail Is Duplicated Across Generated And Authored Pages

Severity: High

Surface: generated `api/cli.md`, `docs/setup.md`, `docs/api/devices.md`, `docs/api/doctor.md`, `docs/api/serve.md`, `docs/api/daemon.md`, `docs/api/recording.md`, `docs/api/logging.md`, `docs/api/actions.md`, `docs/api/selectors.md`, `docs/api/navigation.md`, `docs/api/timeouts.md`

Evidence:

- `/api/cli/` lists command syntax and flags for every command.
- `docs/setup.md` also documents `install`, `operator setup`, `grant-device-permissions`, `doctor`, `devices`, and `snapshot`.
- `docs/api/devices.md` documents `clawperator devices`, `--device`, and `--operator-package`.
- `docs/api/doctor.md` documents `clawperator doctor` flags and defaults.
- `docs/api/serve.md` documents `clawperator serve` flags and endpoints.
- `docs/api/recording.md` documents all recording subcommands and examples.
- `docs/api/logging.md` documents `clawperator logs`.
- `docs/api/actions.md` includes CLI-to-action mapping.
- `docs/api/selectors.md` includes CLI selector examples.
- `docs/api/navigation.md` documents `open` and `wait-for-nav` examples and aliases.
- `docs/api/timeouts.md` documents timeout-bearing CLI commands.

Why it matters for humans:

Duplication makes the docs feel less maintained. When readers see a generated table, a conceptual page, and a how-to page all restating the same command, they cannot tell which one is freshest.

Why it matters for agents:

Agents may retrieve two conflicting or differently scoped snippets and combine them incorrectly, especially when a generated row includes accepted aliases that authored examples intentionally avoid.

Recommendation:

Adopt a source-ownership rule:

- `/api/cli/` owns discoverability only.
- Command concept pages own behavior and failure modes.
- Contract pages own JSON shapes.
- How-to pages own task flow and link outward for details.
- Generated sections own complete enumerations and drift detection, not tutorial prose.

### Finding 5: Generated CLI Flags Are Too Naive To Be A Reader-Facing Contract

Severity: High

Surface: `.agents/skills/docs-build/scripts/generate_cli_reference.py`, generated `api/cli.md`

Evidence:

- `parse_supported_flags()` uses `documentedFlags` when present, otherwise scans the command body for any `--flag` token.
- This pulls flags from help strings, compatibility aliases, error messages, and implementation branches.
- The generated `skills` row surfaces a legacy package-name alias, even though repo terminology rules say "operator" is the public term and that alias is compatibility-only.
- The generated `operator` row lists `--help` but not every global output flag; other rows vary depending on nearby strings.

Why it matters for humans:

The flags column reads like an authoritative contract, but the extraction method is a loose text scan. That mismatch is risky for trust.

Why it matters for agents:

Agents may choose deprecated or secondary aliases because they are displayed with no primary/secondary distinction. They may also miss global flags when a row does not include them.

Recommendation:

Do not show the full flags list in the command index until the registry has structured flag metadata with primary name, accepted aliases, value shape, and canonical owner. In the interim, generate a "Primary syntax" column only and link to authored command pages for flags.

### Finding 6: Action Type Anchors Are Stronger Than Command Anchors, But They Are Not Connected Enough

Severity: Medium

Surface: `docs/api/actions.md`, generated `api/cli.md`, `docs/api/overview.md`

Evidence:

- `docs/api/actions.md` has stable-looking headings for every major action type, such as `### \`click\``, `### \`open_app\``, `### \`wait_for_navigation\``, and `### \`snapshot\``.
- The same page includes `## CLI To Action Mapping`.
- `/api/cli/` does not link command rows to the relevant action sections.
- `docs/api/overview.md` links to Actions generally, not to individual action anchors.

Why it matters for humans:

Someone reading `clawperator open` needs to know when it becomes `open_app` versus `open_uri`. That detail exists, but the generated command page does not guide them there.

Why it matters for agents:

Agents often search for a verb. If they land on `click` in CLI context, they need the execution action shape and selector rules within one or two hops.

Recommendation:

Add generated command-to-action links for flat action commands. For example:

- `click` -> `actions.md#click`
- `type` -> `actions.md#enter_text`
- `read` -> `actions.md#read_text`
- `open` -> `actions.md#open_app` and `actions.md#open_uri`
- `wait-for-nav` -> `actions.md#wait_for_navigation`
- `snapshot` -> `actions.md#snapshot` and `snapshot.md`

Keep the mapping data in a small manifest or structured command metadata, not ad hoc markdown.

### Finding 7: The Result Envelope Needs A More Obvious Canonical Home

Severity: Medium

Surface: `docs/api/overview.md`, `docs/api/errors.md`, `docs/api/snapshot.md`, `docs/api/serve.md`, `apps/node/src/contracts/result.ts`

Evidence:

- `contracts/result.ts` defines `ResultEnvelope`, `StepResult`, `RESULT_ENVELOPE_PREFIX`, and `EVENT_ENVELOPE_PREFIX`.
- `docs/api/overview.md` contains the main result-envelope section.
- `docs/api/errors.md` explains envelope failure shapes.
- `docs/api/snapshot.md` explains envelope placement for snapshot data.
- `docs/api/serve.md` shows execution passthrough responses containing envelopes.

Why it matters for humans:

The result envelope is a core contract, but it is currently embedded inside Overview. A reader may not recognize it as the canonical reference.

Why it matters for agents:

Agents branch on result fields. If envelope fields are scattered across overview, errors, snapshot, and serve pages, agents may confuse wrapper fields with envelope fields.

Recommendation:

Either elevate `docs/api/overview.md#result-envelope` as an explicitly named canonical anchor everywhere, or create `docs/api/result-envelope.md` as a dedicated contract page. Link every wrapper page to that anchor. Keep error-specific guidance on Errors and action-specific success data on Actions.

### Finding 8: Serve Endpoint Coverage Is Useful But Should Be Classified Separately From Node Error Codes

Severity: Medium

Surface: `docs/api/serve.md`, `apps/node/src/cli/commands/serve.ts`, `docs/api/errors.md`

Evidence:

- `serve.ts` defines route-local wrapper codes such as `INVALID_BODY`, `MISSING_EXECUTION`, `INVALID_DEVICE_ID`, `INVALID_OPERATOR_PACKAGE`, `INVALID_PATH`, and `INTERNAL_ERROR`.
- `errors.ts` defines the public Node error enum and does not include those route-local wrapper codes.
- `docs/api/serve.md` documents route-local validation failures and also maps shared `ERROR_CODES` through HTTP status codes.
- `docs/api/errors.md` says only `errors.ts` codes are part of the public error-code contract.

Why it matters for humans:

Readers need to know whether an error code is part of the shared Clawperator error enum or only a serve-layer HTTP wrapper. That distinction exists in prose but could be sharper.

Why it matters for agents:

Agents branching on HTTP responses need different handling for route-local invalid-body failures versus execution failures passed through from `runExecution()`.

Recommendation:

In `docs/api/serve.md`, add a compact "Serve-local error codes" table and explicitly label them as HTTP wrapper codes, not `errors.ts` codes. Link shared execution failures to `errors.md`.

### Finding 9: Setup Is Both A How-To And A Contract Dump

Severity: Medium

Surface: `docs/setup.md`, `docs/api/doctor.md`, `docs/api/devices.md`, `docs/api/environment.md`, `docs/host-agents.md`

Evidence:

- `docs/setup.md` is 410 lines.
- It includes install flow, host-agent artifacts, shared-agent bridge behavior, Android prep, Operator APK install, doctor check list, `DoctorReport` shape, first command, agent sequence, failure table, debugging, and related pages.
- `docs/api/doctor.md` already owns the full `DoctorReport` contract.
- `docs/api/devices.md` owns device resolution rules.
- `docs/api/environment.md` owns env var behavior.

Why it matters for humans:

Setup is the first trust-building page. It is high quality in specificity, but it is long and mixes the happy path with internal artifact and contract detail.

Why it matters for agents:

Agents benefit from exact setup steps, but long pages increase retrieval noise. An agent trying to install may pick up host-agent bridge internals before completing device readiness.

Recommendation:

Keep `docs/setup.md` as the canonical happy path with machine-checkable gates. Move or collapse deep host artifact details behind links to Host Agent Orientation or a dedicated install artifacts section. Keep the full Doctor contract in `api/doctor.md` and link to it rather than restating the shape in Setup.

### Finding 10: Cross-Linking Is Inconsistent And Mostly Page-Level

Severity: Medium

Surface: authored `docs/api/*.md`, `docs/setup.md`, generated `api/cli.md`

Evidence:

- Many pages have good "Related Pages" sections and page-level links.
- Many in-prose command mentions are plain code spans, such as `clawperator snapshot`, `clawperator doctor`, `clawperator devices`, `clawperator record start`, and `clawperator open`.
- Generated `api/cli.md` does not include any links to authored canonical pages.
- Current links generally target pages, not anchors for specific commands, actions, errors, fields, or endpoints.

Why it matters for humans:

Page-level links are helpful but not precise. A reader still has to search within a long page such as Recording, Serve, or Actions.

Why it matters for agents:

Precise anchors improve retrieval and reduce the chance that agents combine unrelated sections from the same page.

Recommendation:

Introduce stable anchors before enforcing links. Then add explicit authored links for high-signal mentions. Avoid broad autolinking at first. A linter can warn on known command names in prose unless the line already contains a link, is a code block, or matches an allowlist.

### Finding 11: Broad Autolinking Would Be Risky Without A Manifest

Severity: Medium

Surface: potential docs-build post-processing, `assemble.py`, authored docs

Evidence:

- Common command names include generic words: `setup`, `install`, `open`, `type`, `read`, `wait`, `press`, `back`, `close`, `sleep`, and `serve`.
- The docs also use these words as ordinary English.
- `assemble.py` currently performs deterministic copy, generation, and marker replacement only. It does not rewrite arbitrary authored prose.

Why it matters for humans:

Noisy links make docs look cheap and distract from the intended reading path.

Why it matters for agents:

Incorrect links can be worse than no links, because agents may treat them as canonical evidence.

Recommendation:

Use explicit links for authored prose and generated links for generated indexes. If autolinking is added, limit it to exact code spans containing full commands or exact action/error identifiers, backed by a manifest. Do not autolink bare generic words.

### Finding 12: Current Generated Anchors Are Incidental And May Be Awkward

Severity: Low

Surface: generated `api/cli.md`, `docs/api/actions.md`, `docs/api/errors.md`, `docs/api/selectors.md`

Evidence:

- Headings use inline code, such as `### \`click\`` and `### \`RESULT_ENVELOPE_TIMEOUT\``.
- MkDocs will derive anchors, but the exact slug behavior for backticks and symbols is an implementation detail of the markdown renderer.
- `api/serve.md` endpoint headings contain spaces and slashes, such as `## \`POST /execute\``.

Why it matters for humans:

Readable URLs and stable fragments make docs easier to share.

Why it matters for agents:

Agents need stable, predictable URLs. Renderer-derived slugs for code headings may change if the theme or markdown extensions change.

Recommendation:

Prefer explicit HTML anchors or predictable generated heading text where stable fragments matter. Examples:

- `<a id="command-snapshot"></a>`
- `<a id="action-open_app"></a>`
- `<a id="error-result-envelope-timeout"></a>`
- `<a id="endpoint-post-execute"></a>`

Do this selectively for public canonical anchors, not every heading.

### Finding 13: Error Code Table Is Complete But Too Thin As A Standalone Entry Point

Severity: Low

Surface: `docs/api/errors.md`, `.agents/skills/docs-build/scripts/generate_error_table.py`, `apps/node/src/contracts/errors.ts`

Evidence:

- The generated error table lists every code from `ERROR_CODES`.
- Many generated rows have notes of `-` because the enum comments are sparse.
- The authored page adds recovery families and key cases, but not every generated code has a canonical detailed anchor or recovery note.

Why it matters for humans:

The table looks complete but many rows are not actionable on their own.

Why it matters for agents:

An agent landing on a less-common code such as `EMULATOR_BOOT_TIMEOUT` or `OPERATOR_CHECKSUM_FAILED` may not get enough recovery guidance.

Recommendation:

Keep the generated complete enum table, but add stable anchors for each code and group-level recovery sections. For less-common codes, a short one-line recovery category is enough if a deeper page owns the details.

### Finding 14: The Docs Are Strong On Contracts But Weak On Command-Level Canonical Examples

Severity: Medium

Surface: `docs/api/actions.md`, `docs/api/selectors.md`, `docs/api/serve.md`, `docs/api/recording.md`, generated `api/cli.md`

Evidence:

- Actions page has rich JSON examples for action payloads.
- Selectors page has CLI examples for selector forms.
- Recording and Serve have many endpoint or subcommand examples.
- Generated CLI page has no examples beyond syntax, no output shapes, and no failure modes.
- There is no consistent command detail template saying purpose, primary usage, output shape, failure modes, and canonical contract links.

Why it matters for humans:

Readers can find detailed contracts, but not always a polished per-command recipe.

Why it matters for agents:

Agents often need one reliable command example plus output field paths. The current command index does not provide that, and authored pages vary by surface.

Recommendation:

Create a command-detail schema for authored pages where a command is important enough to own behavior:

- Purpose
- Primary command
- Inputs and defaults
- Output shape
- Failure modes
- Verification pattern
- Related action, selector, error, result-envelope links

Do not create one page per trivial command immediately. Start with high-traffic commands: `snapshot`, `click`, `open`, `doctor`, `devices`, `operator setup`, `serve`, `recording`, `skills run`, and `mcp serve`.

### Finding 15: Navigation Is Compact But The API Section Needs A Stronger Reading Order

Severity: Low

Surface: `sites/docs/mkdocs.yml`, `docs/index.md`

Evidence:

- API nav currently orders CLI Reference before Actions, Selectors, Snapshot Format, Errors, Devices, Doctor, Timeouts, Environment Variables, Serve API, Daemon, MCP, Navigation Patterns, and Recording Format.
- `docs/index.md` mirrors that rough order.
- The generated CLI page is currently dense, so placing it near the top makes it a first impression for the API.

Why it matters for humans:

The first API reference page a reader opens can feel like a generated dump instead of a designed guide.

Why it matters for agents:

Agents following nav order may retrieve `/api/cli/` before the more useful Overview, Actions, and Selectors pages.

Recommendation:

After simplifying `/api/cli/`, keep it near the top as a directory. Until then, consider making Overview the stronger routing page and label CLI Reference as "Command Index" in nav.

### Finding 16: Some Existing Docs May Be Compensating For API Friction

Severity: Medium

Surface: docs about CLI aliases and command forms, `apps/node/src/cli/registry.ts`, `docs/internal/design/node-api-design-guiding-principles.md`

Evidence:

- The API Agent UX guidance says the command an agent tries first should work, and docs-only fixes are insufficient when the API rejects intuitive forms.
- `registry.ts` already accepts many synonyms, such as `tap` for `click`, `fill` for `type`, `open-url` for `open`, `record` for `recording`, and `execute` for `exec`.
- Generated docs expose aliases and compatibility forms heavily, but do not clarify primary forms versus accepted forms.

Why it matters for humans:

Showing every accepted synonym makes the API look less intentional.

Why it matters for agents:

Agents need one primary form to copy, plus forgiving parser behavior when they guess. Listing every alias can cause them to learn the wrong primary vocabulary.

Recommendation:

Document one primary command and one primary flag form. Keep accepted aliases in parser behavior and tests. Mention aliases only in compact compatibility notes or generated machine-readable metadata. If an authored page has to repeatedly warn about a non-obvious syntax, consider whether the CLI should accept the obvious syntax or emit a teaching error.

## Recommended Link and Anchor Strategy

Stable anchors should be created for public concepts agents and humans will cite or retrieve directly.

Recommended anchor classes:

| Class | Anchor pattern | Canonical owner |
| --- | --- | --- |
| CLI command | `command-<name>` | `/api/cli/` index row, linking to detail owner |
| CLI subcommand | `command-<name>-<subcommand>` | detail owner, such as Recording or Setup |
| Execution action | `action-<type>` | `api/actions.md` |
| Selector field | `selector-field-<field>` | `api/selectors.md` |
| Selector CLI flag | `selector-flag-<flag-name>` | `api/selectors.md` |
| Error code | `error-<lowercase-code>` | `api/errors.md` |
| Result envelope field | `result-envelope-<field>` | `api/overview.md` or future `api/result-envelope.md` |
| Serve endpoint | `endpoint-<method>-<path>` | `api/serve.md` |
| Setup step | `setup-step-<slug>` | `setup.md` |

Cross-linking policy:

- Authored prose should use explicit markdown links for high-signal mentions, especially first mention in a section.
- Generated indexes should link every row to its canonical owner.
- Code blocks should not be autolinked.
- Generic bare words should not be autolinked.
- Exact code spans can be linted, but the linter should start warning-only with an allowlist.

Implementation options:

| Option | Use where | Benefits | Risks |
| --- | --- | --- | --- |
| Explicit authored links | Narrative docs, examples, related pages | High precision, good editorial control | Requires maintenance |
| Generated command/action indexes | `/api/cli/`, possible action index | Accurate and drift-resistant | Needs structured metadata |
| Docs-build post-processing | Exact code spans only, if ever | Can reduce manual work | High risk of noisy or wrong links |
| Lint/check for unlinked names | CI or docs build validation | Finds omissions without rewriting prose | Needs allowlist for examples and generic words |
| Limited autolinking in generated sections | Generated CLI/action/error tables | Safe because source tokens are known | Must avoid aliases becoming canonical by accident |

Recommendation: start with explicit authored links plus generated links in generated indexes. Add a warning-only linter next. Avoid broad post-processing.

## Recommended CLI Reference Strategy

`/api/cli/` should become the command directory for the whole CLI. Its job is to answer "what command exists and where do I go for the contract?"

Recommended structure:

```markdown
# CLI Command Index

This page is generated from `apps/node/src/cli/registry.ts`.

## Commands

| Command | Primary usage | Summary | Details |
| --- | --- | --- | --- |
| `snapshot` | `clawperator snapshot [--device <id>]` | Get current Android UI hierarchy as XML. | [Snapshot Format](snapshot.md#command-snapshot), [Action](actions.md#action-snapshot) |
```

What to include:

- command name
- primary syntax only
- one-line summary
- canonical detail link
- optional subsystem group
- optional "common next command" only if generated from metadata

What to omit or de-emphasize:

- every alias inline
- every accepted flag inline
- long subcommand syntax lists in a single table cell
- per-command repeated bullet blocks that restate the same table
- compatibility-only aliases at the same level as primary flags

Where detailed behavior should live:

- `setup.md` or a future `api/operator.md` for `operator setup`, `install`, and host setup behavior
- `api/devices.md` for `devices` and `--device`
- `api/doctor.md` for `doctor`
- `api/snapshot.md` for `snapshot`
- `api/actions.md` for execution action payloads
- `api/selectors.md` for selector flags
- `api/serve.md` for `serve`
- `api/daemon.md` for daemon commands
- `api/recording.md` for recording commands
- `api/mcp.md` for `mcp serve`
- skills pages for `skills` commands

Generated accuracy should be preserved by adding structured metadata, not by printing raw parser scans. A future generator can fail if a command lacks a canonical detail target.

## Implementation Phases

### Phase 1: Declare Canonical Ownership

- Add a small docs IA manifest, either YAML or Python data, mapping command names, action types, error codes, selector flags, and serve endpoints to canonical docs targets.
- Do not change docs content yet except adding the manifest and tests if desired.
- Review the manifest manually for high-traffic commands first.

### Phase 2: Simplify `/api/cli/`

- Update `generate_cli_reference.py` to render one command index table only.
- Add a `Details` column from the manifest.
- Remove grouped duplicate tables and per-command repeated bullets.
- Keep all data generated from code or manifest.

### Phase 3: Add Stable Anchors On Existing Canonical Pages

- Add explicit anchors for high-traffic commands, action types, error codes, and serve endpoints.
- Prefer narrow changes to existing pages.
- Do not split pages yet unless an anchor cannot be made clear.

### Phase 4: Link High-Signal Mentions

- Update first mentions of known commands, actions, selectors, errors, and endpoints to link to canonical anchors.
- Prioritize `docs/index.md`, `docs/setup.md`, `docs/api/overview.md`, `docs/api/actions.md`, `docs/api/selectors.md`, `docs/api/errors.md`, `docs/api/devices.md`, `docs/api/doctor.md`, `docs/api/serve.md`, and `docs/api/recording.md`.
- Keep examples as code blocks without inline links.

### Phase 5: Reduce Duplication Page By Page

- Setup: keep the happy path, collapse deep contract detail behind links.
- Actions: keep JSON action contracts, link out for CLI command behavior.
- Devices and Doctor: keep contract detail, remove repeated setup prose.
- Recording and Serve: keep endpoint or subcommand detail, link to shared result/error/selector pages.

### Phase 6: Add Docs Lints

- Add a warning-only check for unlinked known identifiers in authored prose.
- Add a check that generated command index rows have valid canonical targets.
- Add a check that public error codes and selector flags have stable anchors.
- Promote warnings to failures only after the first cleanup pass.

## Open Questions

1. Should `ResultEnvelope` stay canonical in `api/overview.md#result-envelope`, or should it become a dedicated `api/result-envelope.md` page?
2. Should command detail anchors live mostly on existing concept pages, or should high-traffic commands get dedicated command pages?
3. Should `/api/cli/` be renamed in nav to "Command Index" while keeping the stable URL `/api/cli/`?
4. How much alias information should be public? One option is "primary forms in docs, accepted aliases in generated metadata only."
5. Should serve-local wrapper error codes be treated as a separate public contract with generated coverage, or remain authored in `api/serve.md`?
6. Should the docs build own a command/action/link manifest, or should that metadata live closer to `apps/node/src/cli/registry.ts` so code and docs cannot drift?
7. Should setup internals such as host-agent artifacts remain on `docs/setup.md`, move to `host-agents.md`, or become an install-contract page?
8. Should `skills` command details live under API or Skills? The command is registered in the CLI, but the user intent is skill discovery and runtime.
